# TIP — Typst Inline Preview

## Project Overview

TIP is an Emacs minor mode that renders Typst math fragments as inline SVG previews, inspired by org-latex-preview. This workspace contains the original implementation and an in-progress rewrite.

## Architecture (v2 — in progress)

Replacing the Python server with a native Rust binary. See `tip-server/` and the plan at `.claude/plans/iridescent-questing-whisper.md`.

**Communication**: tip.el ↔ tip-server uses **JSON-RPC over stdio** — Emacs spawns tip-server as a child process and exchanges JSON-RPC messages through Unix stdin/stdout pipes (newline-delimited framing). Same pattern as LSP. Replaces the old JSON-RPC over HTTP (localhost TCP) approach.

**Future transport options** (tip-core is transport-agnostic, so these are independent of core logic):

1. **Emacs dynamic module**: Compile tip-core into a `.so` loaded directly by Emacs. No IPC, no serialization. Tradeoffs: fastest possible path but harder to test (need Emacs) and less crash-safe (Rust panic kills Emacs).

2. **emacs-lsp-booster integration**: Our JSON-over-stdio protocol is compatible with [emacs-lsp-booster](https://github.com/blahgeek/emacs-lsp-booster) (.ref/eglot-booster-ref/). This Rust wrapper buffers I/O and optionally pre-compiles JSON into Emacs bytecode.

Strategy: get everything working and tested with JSON-RPC over stdio first, then evaluate these optimizations while keeping tip-core unchanged.

**Compilation approach**: Emacs sends full buffer content via `sync`. For each math fragment, tip-server builds a synthetic Typst document preserving the fragment's scope context, compiles it via `typst::compile`, and returns inline SVG + height/depth for baseline alignment.

**Key types**:
- `TipWorld` (tip-core/src/world.rs): implements `typst::World` with in-memory sources, embedded+system fonts, custom font dirs, package resolution
- `FragmentCompiler` (tip-core/src/compiler.rs): builds fragment source, compiles to SVG, measures baseline, crops SVG
- `Handler` (tip-server/src/handler.rs): dispatches protocol messages to core, sets project root from URI
- Protocol messages defined in tip-protocol/src/messages.rs

## Baseline Alignment — The Hard Problem

This was the most complex part of the project. The goal: inline math SVGs should sit on the same baseline as surrounding Emacs text, and ALL math fragments should have consistent baselines relative to each other.

### What we tried and why it failed

1. **Kodama's `bounded()` technique** (`text(top-edge: "bounds", bottom-edge: "bounds", eq)`): Forces Typst to use actual glyph ink bounds instead of nominal line metrics. **Fixed clipping** (subscripts, tall fractions no longer cut off). But **broke baseline consistency**: `bounded()` changes the frame coordinate system differently per expression. Simple `$a+b$` has baseline at 89% from top, but `$a_b$` has it at 64%. The two groups are each internally consistent but offset from each other.

2. **Frame `baseline()` field**: Typst's `Frame` struct has a `baseline` field, but it's only set on inner content frames, not page frames. Walking the frame tree to find `has_baseline()` returned `None` for all frames in our compiled output.

3. **First text item y-position**: Text items in the SVG frame are positioned at their baseline y-coordinate. Using the first text item works for simple expressions but gives inconsistent results with `bounded()` because the coordinate origin shifts per expression.

4. **Various ascent formulas**: Tried `100*(1-depth/height)`, reference-x-based, fixed-depth, font-metrics-based corrections. None produced consistent alignment across all expression types simultaneously.

5. **Emacs `:ascent center`**: Centers the image in the line, NOT at the baseline. Looks OK for simple math but wrong for subscripts/fractions.

### The working approach: Render → Crop → Align

The solution combines three ideas:

**Step 1: Render WITHOUT `bounded()`, with generous margins (20pt top/bottom)**
- Without `bounded()`, Typst uses standard text metrics for layout
- The math baseline is at a CONSTANT position from the page top for ALL expressions
- This position = `margin_top + font_ascent` ≈ 27.5pt for 11pt text with 20pt margin
- Simple expressions, subscripts, superscripts, fractions — all have the same baseline_y
- The generous margins ensure nothing is clipped, even deeply nested fractions

**Step 2: Find the ink extent by walking the frame tree**
- After compilation, scan all text items and shape items in the page frame
- Compute the min/max y-positions (with estimated glyph ascent/descent)
- This gives the actual ink bounding box within the large-margin page

**Step 3: Crop the SVG viewBox to the ink bounds**
- Rewrite the SVG's `viewBox` and `height` attributes to show only the ink region + 0.5pt padding
- The result: tight image (no wasted margin space) but with all content visible

**Step 4: Compute ascent from the baseline position within the cropped image**
- `baseline_in_crop = baseline_y - crop_top`
- `ascent_pct = baseline_in_crop / cropped_height * 100 - tip-baseline-offset`
- `tip-baseline-offset` (default -2) is a user-tunable correction for Emacs font metric differences

**Why this works**: The baseline_y is determined by the NON-bounded layout, so it's constant across all expressions. The cropping is post-render, so it doesn't affect the layout. The ascent percentage varies per expression (taller images have lower ascent %) but the ABSOLUTE baseline position (in pixels from the line top) is the same.

### Baseline text item selection

For finding the baseline y-position in the frame tree:
- Walk all text items, track the one with the **largest font size** (primary math content, not sub/superscripts)
- On font-size ties, prefer the item **closest to the page midpoint** (handles fractions where both numerator and denominator are at reduced size — the midpoint is near the fraction bar, which is the correct baseline)

### User calibration

The `tip-baseline-offset` defcustom lets users fine-tune the overall vertical position:
```elisp
(progn (setq tip-baseline-offset -2) (tip-render-all))
```
Adjust the number and C-x C-e until baselines align with surrounding text. The offset depends on the Emacs font; -2 works well for Adwaita Mono 11pt.

### Scaling

Emacs `(N . em)` in image `:height` means `N * frame-char-height` pixels. `frame-char-height` corresponds to the font's point size at screen DPI. So:
```
height_em = svg_height_pt / emacs_font_pt * tip_scale
```
`tip-scale` defaults to 1.0. `emacs_font_pt` is read from `(face-attribute 'default :height)` divided by 10.

The preamble sent to the server includes `#set text(size: Xpt)` matching the Emacs font size, so the Typst rendering matches the surrounding text scale.

## Scope-Aware Compilation

**Approach**: Parse document AST, walk tree collecting only scope-defining nodes (LetBinding, SetRule, ShowRule, ModuleImport, CodeBlock openers/closers, ContentBlock openers/closers). Skip all content (text, other math). Append the target fragment + closing delimiters. This produces a minimal document that compiles just the fragment with its full scope context.

**Handles**: deep mode nesting (math→code→markup→math...), variable shadowing, closures, conditional lets, show rule transforms, nested `#import` from relative files + `@local/` packages + `@preview/` packages.

**Nested math filtering**: Tree-sitter query `((math) @math)` returns ALL math nodes including nested ones (e.g. `$a + #text[$b$]$` returns both outer and inner). The fragment collector filters out nested ranges to only compile outermost fragments.

## Auto-Toggle Overlay System (preview-toggle.el)

Extracted into a generic reusable framework. See `tip/PREVIEW-TOGGLE.md` for flow diagrams.

**Key design**: Uses `pre-command-hook` and `post-command-hook` to detect cursor transitions:
- Outside → inside: open overlay (reveal source)
- Inside → outside: close overlay (recompile, show image)
- Fragment → fragment: close old, open new

**Boundary detection pitfall**: `tip--get-bounds-of-math-at-point` must use strict `< x (cdr range)` (not `<=`) for the end bound. The position at `(cdr range)` is AFTER the closing `$`, which is outside the fragment. Using `<=` causes the pre-command hook to incorrectly mark cursor as "inside math" when it's at the boundary.

**Overlay detection**: Uses `overlays-in pos (1+ pos)` in addition to `overlays-at pos` to handle Emacs's half-open overlay intervals at boundaries.

## Typst-Specific Conventions

- **Math fonts require OpenType MATH tables**. Regular text fonts don't work for math.
- **Setting math font**: `#show math.equation: set text(font: "FontName")` — NOT `#set text(font: ...)` which only affects text, not math.
- **Block vs inline detection**: block math starts with `$ ` (dollar + space), inline is `$...$`.
- **Typst syntax only** — never use LaTeX commands. E.g. `arrow.hook.r` not `\hookrightarrow`.
- **Single-letter math identifiers**: `$x$` is always italic x, NOT a code variable reference. Multi-char names (`$foo$`) DO resolve from scope. Use `#let bb = sym.beta` then `$bb$`.

## Published crate API vs git HEAD

The cloned typst-ref/ is git HEAD but we depend on published crates (typst 0.14.2). APIs differ:
- `FontSearcher::new().search()` returns `Fonts { book, fonts }` (published) — no `FontStore` struct
- `FileId::new_fake(VirtualPath)` not `FileId::unique(RootedPath)`
- `Source::new(id, String)` — takes owned String, not &str
- `document.pages` is a field, not `.pages()` method
- `fn today(&self, offset: Option<i64>)` not `Option<Duration>`
- `id.vpath().as_rootless_path()` not `.get_without_slash()`

Always check the published API, not the cloned source.

## Known Typst Limitations

**Page clipping with `height: auto`**: Typst's auto page height doesn't fully account for glyph ink bounds beyond the content box. Upstream: https://github.com/typst/typst/issues/1028. Solved by rendering with large margins (20pt) and cropping SVG to ink bounds post-render.

## Kodama Compatibility

TIP works with files targeting kodama's HTML export (`#show: kodama`). Key issues solved:

- **Page setting override**: kodama's show rule sets `page(paper: "iso-b6", margin: 2em)` for paged output. TIP's `page_setup` is emitted AFTER the skeleton (which contains `#show: kodama`) so it overrides with `width: auto`. This was a critical ordering fix — the skeleton contains show rules from the document, and page setup must come last.

- **Scope extraction**: `#show: kodama` and `#show: preamble` are ShowRule nodes, preserved by the scope skeleton. The math show rules inside kodama (for HTML baseline) have no effect in paged mode (they check `export-target`).

- **`html.elem`, `html.frame`**: These functions only work with HTML export. In paged mode (what TIP uses), they produce content or are no-ops. Math inside `html.elem(...)` containers compiles fine because the skeleton strips the container.

## Future: CeTZ and Fletcher Diagram Preview

CeTZ (`@preview/cetz`) and Fletcher (`@preview/fletcher`) produce diagrams, not inline math. Key differences from math preview:

### What needs to change

1. **Detection**: Math fragments are detected via tree-sitter `((math) @math)`. Diagrams are function calls like `cetz.canvas(...)` or `fletcher.diagram(...)`. Need a new tree-sitter query or AST pattern to detect them.

2. **Compilation**: Diagrams need their full argument structure preserved, not just scope context. The scope skeleton must keep the entire `cetz.canvas(...)` or `diagram(...)` call, not strip it like we strip `#list[...]`.

3. **Page setup**: Diagrams need `width: auto, height: auto` with generous margins. No baseline alignment needed — they're block elements.

4. **Display**: Diagrams are block elements, use `:ascent center`. May want to limit max width/height.

5. **Imports**: CeTZ and Fletcher are `@preview` packages. The `PackageStorage` already resolves them. The scope skeleton preserves `#import "@preview/cetz:0.4.2"`.

### Architecture approach

The cleanest approach: extend `FragmentCompiler` with a `compile_diagram` method alongside the existing `compile_fragment` / `compile_fragment_scoped`. The diagram compiler:

1. Takes the full function call source (e.g., `cetz.canvas(length: 1cm, { ... })`)
2. Extracts scope context the same way as math (the skeleton)
3. But preserves the ENTIRE diagram call in the skeleton (don't strip it)
4. Compiles to SVG with `width: auto, height: auto`
5. Returns SVG + dimensions (no baseline measurement)

On the Emacs side:
- `preview-toggle.el` already supports any preview type via `preview-toggle-type`
- Add a new fragment collector for diagrams (tree-sitter query for FuncCall matching known diagram functions)
- Use `tip--make-image-spec` with `display-p = t` (center aligned)

### Key files to modify

| File | What to add |
|------|-------------|
| `tip-core/src/compiler.rs` | `compile_diagram_scoped()` method, diagram-aware skeleton |
| `tip-protocol/src/messages.rs` | `compile_diagrams` request type |
| `tip-server/src/handler.rs` | Handler for diagram requests |
| `tip/tip.el` | Diagram fragment collection, overlay creation |

### CeTZ specifics

CeTZ diagrams use `cetz.canvas(...)` which takes a closure with draw commands. The entire closure must be preserved. Example:

```typst
#cetz.canvas(length: 1cm, {
  import cetz.draw: *
  line((0,0), (1,1))
  circle((0.5, 0.5), radius: 0.3)
})
```

The scope skeleton must keep `#cetz.canvas(length: 1cm, { import cetz.draw: *; ... })` — the function call, its arguments, and the code block body.

### Fletcher specifics

Fletcher diagrams use `fletcher.diagram(...)`:

```typst
#fletcher.diagram(
  node((0, 0), $A$),
  node((1, 0), $B$),
  edge((0, 0), (1, 0), "->"),
)
```

Similar to CeTZ — preserve the full call. Note: Fletcher diagrams contain MATH inside `node(...)` — those inner math nodes should NOT be compiled separately as inline math (they're part of the diagram).
